## 2. Hard rules

A change that breaks any of these cannot be merged.

1. **Layering.** Skill scripts and adapters import only `core` and `contracts`. A new shared module goes in `core/` with a steward in `core/OWNERS.json`.
2. **Experiment names.** No experiment names in `skills/` or `contracts/` (ALICE included; `check_layering.py`). Use citation keys where needed.
3. **Python uses only the standard library** (a design choice for the Geant4 scripts). No Python bindings.
4. **C++ dependencies.** `simcore` uses only the C++17 standard library and the existing `MiniJson.hh`, and does not link Geant4. `layered_sim` and `simroot` link Geant4; ROOT files are written and read by the g4tools code shipped with Geant4, with no ROOT installation.
5. **G5 licence boundary.** Python exchanges only JSON and CSV with separate executables. Code is written from the Geant4 API; no Geant4 example code is copied or adapted.
6. **Statuses and exit codes** (`core/status.py`): 0 ok, 1 a negative verdict (`refused`/`failed`), 2 unusable input (`rejected`), 3 `incomplete`. No other exit code; "unresolved" is always 3, never 1.
7. **Execution trace.** New record writers call `trace.provenance()`; new shared functions call `trace.tag()`.
8. **Size and paths.** `check_packaging.py`: each file ≤ 2 MiB, all text files scanned; written paths go through `tilde()`. The size statement in the plugin README must be within 10 % of the actual value.
9. **Entry-point budget.** hep-detector quick load ≤ 25,600 bytes (24,669 now); description ≤ 1,024 characters (1,018 now). This task does not change `skills/hep-detector/SKILL.md` or the description.
10. **Process.** Phase 1 follows the sci-fix process; phase 2 the adapter-change process; both follow the release steps. Work only on the branch `worktree-geant4-architecture`; do not push to `main` or open a pull request without the maintainer's approval.
11. **Contract versions.** New rules are gated with `strict or _at_least(contract_version, C1)`, with no warning branch; the version number is fixed only at merge time.

## 4. Design principles

1. **Correctness before extension.** No new feature is merged before phase 1.
2. **The study core knows only data.** Rules, gates and benchmarks read through the column map and the probe output, never backend-specific column names or UI command strings.
3. **Trust the actual state; declarations are only the fallback.**
4. **Stopping rules and grids of evidence are declared in advance.** Topping up, refining and redoing controls are never decided from gate or benchmark results.
5. **Look for an existing implementation first.** Reuse what the plugin has; an oracle never imports the module it tests.
6. **Minimal change.**
7. **Follow the existing rules** (section 2).
8. **The backend describes itself.** layered_sim writes its own column map and its effective settings at run time.
9. **The validation grade follows the nature of the reference.** A reference that is an exact consequence of the inputs (analytic helix, kinematics, least-squares algebra) makes a check verification, which cannot upgrade; only a physics model Geant4 approximates (Bethe, Landau–Vavilov, Highland, shower profiles) or a published measurement can be reference or sanity.
10. **Upgrade-relevant facts are decided by the contract.** Grade, kind and configuration are never self-declared by a record.
11. **Language split.** Every computation that turns simulation output into numbers (per-event and per-run reductions, estimators and their SE, fits) is in C++; formulas that compute reference values from physics inputs, threshold comparisons and decisions, records and provenance, and the contracts are in Python. No quantity has a production implementation in both languages; one in the other language may exist only in tests, as an oracle.

### A1.2 Scope check (D1)

**Change:** `contracts/validate.py` (the single implementation, exported); `check_geant4_study.py` (imports it and drops `scope_within()`; `label` writes `declared_scope.observable_kind`); the study-spec schema.

**Rules:**
- Compare the controlled `observable.kind`, not free text (free text stays for people).
- `label` copies the study spec's `observable.kind` into `declared_scope.observable_kind`; it must be among the supported kinds of the counted benchmarks. The study spec's `validation_plan.scope` is `additionalProperties: false`, so the schema must add `observable_kind`.
- Dimensions compared: observable kind, particle, material, energy, thickness; a scalar is `[v, v]`.
- Every dimension present in the benchmark scope must be present in the declared scope; a missing one is outside.
- The scope of `longitudinal-profile` has only particle and energy (the tool writes null material and thickness). Compare those two, the kind and the **target-geometry hash**: the declared scope must carry the same `target_geometry_sha256` as the benchmark (A1.3). Comparing only particle and energy would let any material stack borrow the published stack's result to upgrade (the prototype showed this hole). The energy is a scalar, so the declared energy range must equal it.
- Gating: `strict or _at_least(contract_version, C1)`, no warning branch. Records at contract 3.5.0 or below meet the new rules only under `--strict`, and only records with `validated-in-scope` fail (`_study_upgrade` returns early for others).

### A1.3 configuration and the isolation rule

**Change:** `geant4_benchmarks.py` (output); `contracts/validate.py` (rule); `contracts/dependencies.py` (re-derivation).

**Rules:**
- `geant4_benchmarks.py` writes `configuration`, `target_geometry_sha256` and `configuration_basis` for every benchmark result, derived from the geometry of the run record named by the benchmark config's `run_record`, never from user input. A benchmark that counts toward an upgrade must have `run_record` (optional today).
- **Target:** the benchmark config declares `target_slabs` (names of the slabs in the target, absorbers included). A single-layer benchmark defaults to the measured slab. `longitudinal-profile` must list the whole sampling stack: its `layers` list only readout columns, without absorbers, so the target cannot be derived; derived literally, the real sampling stack always comes out `embedded`.
- **`isolated`** when: no field, a vacuum world (`G4_Galactic`; J14 complies), and every placement other than the world belongs to `target_slabs`; otherwise `embedded`. spec/1 has no field entry and counts as field-free; spec/2 decides by an explicit `field` block, and from phase 2 the probe's recorded field is checked as well.
- **`target_geometry_sha256`:** the sha256 of the target's normalized list (ordered slabs, thickness, transverse size, material composition and density; numbers as `repr`; repeated placements listed one by one); the same for spec/1 and spec/2.
- **Contract rule (C1, gated as in A1.2):** every counted benchmark must have `configuration == "isolated"`; missing or `embedded` is an error. `dependencies.py` **must** re-derive configuration and hash from the run records in `evidence_records` and compare with the record (otherwise configuration is self-declared, like the grade was).
- The prototype confirms configuration can be derived from the existing recorded run records, so J14 needs only an offline replay.
- **Residual limits (written into the protocol):** J14's recorded CSVs are reduced, so their hashes do not match `output_hashes` of the run records; configuration describes the run record the config **names**, not one proven to have produced the CSV. The geometry of negative-control runs is not checked separately.

### A1.4 Negative controls (D3)

**Change:** `geant4_benchmarks.py`.

- The decision quantity is the actual shift in the observable: `shift = (control − nominal) / reference`, with the SE combined from both runs.
- At the detection limit: `caught` and `|shift| ≤ 1.1 × DL`.
- Inject both signs; otherwise restrict the claim to one sign, recorded in `scope.detection_limit_sign`.
- J14's existing controls inject only +density. First restrict both J14 claims to one sign (`detection_limit_sign: "+"`); per the prototype both already satisfy `|shift| ≤ 1.1 × DL` (MPV 0.0856 against DL 0.0827; stopping power 0.0381 against 0.0378). Add the negative controls in the live re-record.

### A1.5 Convergence gate and reporting (D4)

**Change:** `convergence()` and `cmd_run` in `check_geant4_study.py`.

"Pass only if every observable is equivalent" is an intersection-union test:

```
pass:  |diff| + q_pass · se ≤ tol
fail:  |diff| − q_fail · se > tol
else:  unresolved
```

| Item | Rule |
|---|---|
| se | the SE of the **difference** |
| q_pass | se from sub-runs: t₀.₉₅(ν); from a large-sample bootstrap: z₀.₉₅ = 1.645 |
| q_fail | as above, at quantile 1 − α/m, with m the number of (parameter × observable) pairs |
| ν | for the difference of two estimates with K = 16 sub-runs each, Welch's approximation gives about 30 (t₀.₉₅(30) = 1.697); 15 for a single estimate |
| event count | set in advance so that the se of the difference ≤ tol/4 |

Operating characteristics (se = tol/4 treated as known, α = 0.05):

| True difference | pass | fail (m = 1) | fail (m = 6) | fail (m = 30) |
|---|---|---|---|---|
| 0 | 0.981 | 0.000 | 0.000 | 0.000 |
| tol/2 | 0.639 | 0.000 | 0.000 | 0.000 |
| tol | 0.050 | 0.050 | 0.008 | 0.002 |
| 2 tol | 0.000 | 0.991 | 0.946 | 0.857 |

At a true difference of tol/2 the power to pass is only about 64 %; this is the price of fixing se ≤ tol/4 in advance, and the documentation says so.

**Reporting:** unresolved is reported as run status `incomplete` (exit 3), and the artifact label stays `unvalidated`; only fail is `failed` (exit 1). Today `convergence()` and `cmd_run` treat every non-pass as `failed`; this must change.

### A1.6 MPV estimator and SE (D5)

- The nominal sample is produced as K = 16 chunks (calling `geant4_run.py chunk` with a hand-built partition manifest), N events in total. This is **not** a split of the existing single nominal run: every chunk has new events, so J14's nominal needs a live re-record. The full sample is the concatenation (`concat`) of the chunk CSVs.
- The reported value becomes **the mean of the 16 sub-run MPVs**; fixed bin width written into the spec; SE = sd(sub-run MPVs) / √16; t₁₅ quantiles.
- The full-sample MPV is only a diagnostic; its difference from the mean goes into the record. Reason: a histogram-mode estimator does not scale as 1/√N, and sd/√K holds only for the mean of sub-run MPVs; a reviewer's toy shows it underestimates the full-sample MPV's spread by a factor 1.1 to 2.3, depending on bin width.
- The bootstrap is no longer used for the MPV.
- Sub-run MPVs are computed from each chunk CSV separately, never through the partition merge rules (`mpv` is not in `NON_ADDITIVE_TOKENS`; as a numeric chunk key it would be silently summed).

### A1.7 Two-stage event count

- `N = ceil(N_trial · (SE_trial / target)² · f)`.
- "Target missed" is judged on the **estimated** SE of the evidence run. When both trial and evidence SEs come from K = 16 sub-runs, the probability of meeting the target is P(F₁₅,₁₅ ≤ f): only 0.636 at f = 1.2, so **f = F₀.₉₀(15,15) ≈ 1.97** (90 %).
- With a large-sample bootstrap SE, f = 1.2.
- An evidence run that misses its target is unresolved (`incomplete`, exit 3) and **must not be topped up**.

### A1.8 Seeds

- `H(study_id, role, point_id, k)` maps to **one** integer in [1, 2³¹) (the C++ reads seeds as double; beyond 2⁵³ precision is lost). Roles: trial, nominal, scan, control, variation, calibration; k is the chunk index; positive and negative controls use different point_ids.
- chunk: the study builds the manifest by hand, each chunk's seed is H; layered_sim's second seed keeps `start + 1` from `cmd_chunk`. Do not use `make_manifest`'s `seed × 100003 + k`.
- scan: each point's seed is H, replacing `cmd_scan`'s `[s0, s1 + k]`.
- Checks: `validate_manifest` rejects only duplicate seeds within one manifest; `check_geant4_study.py` also checks that no seed pair repeats across all run records of a study.

### A1.9 Bootstrap, evidence correlation (D7) and execution trace

- **Bootstrap** (for means, quantiles, fractions): Poisson(1) weights from a 64-bit counter hash (study_seed, run_id, chunk_id, event_id, replica_id) via the inverse CDF; R ≥ 400; `summarize` checks for duplicate event keys.
- **Evidence correlation:** `extension.study.evidence_overlap` lists the runs shared by several decisions, with `evidence_overlap_version`.
- **Trace tags** (lower-case, hyphenated): scope comparison `geant4-scope-kind`, configuration derivation `geant4-configuration`, IUT gate `geant4-convergence-iut`, sub-run MPV `geant4-mpv-subrun`, seed hash `geant4-seed-hash`. Advisory scans do not read tags yet, but later advisories can use them to tell whether affected code ran. Once `check_geant4_study.py` imports `contracts.validate`, `code_paths` gains `contracts/validate.py` and others; this is expected. From phase 2 the sub-run MPV and bootstrap run in `simstat`, and the Python interface that calls it records the tags.

## 7. Phase 2: C++ compute core (adapter 0.2.0)

### A2.1 Scope

All C++ work that affects J14 happens in this phase: reading spec/2, scorer components, the probe, the column map, per-event ROOT files and `simroot`, and moving the computation of observables and statistics from Python to `simcore`. The field region and plane crossings come in task B (mixtures already exist in 0.21.0).

### A2.2 spec/2 coordinates and format

- Coordinates have the world centre as origin, the stacking axis is x, units are mm.
- `at_mm` is the x coordinate (world frame) of an element's **front face**. A daughter's `at_mm` is also in the world frame and must lie inside its mother.
- Only one level of nesting.
- The schema uses only keywords supported by `contracts/schema.py` (including the three added in this phase, A2.5).
- Gun fields: `energy_MeV` (task B adds `ekin_per_nucleon_MeV`).
- **Reserved for task B:** the schema defines an optional `field` block; in this phase `layered_sim` rejects a non-empty `field` (`rejected`, exit 2). A1.3 already classes a geometry with a `field` as `embedded`.

### A2.3 spec/1 → spec/2 conversion and bit-identical output

spec/1 always goes through the C++ `simspec convert` first; `layered_sim` reads only spec/2. The conversion must keep simulation output bit-identical on the same host:

| Factor | Changes events? | Conversion rule |
|---|---|---|
| Material construction | **yes** (mixtures add components in order through `G4Material::AddMaterial`; the order fixes the element vector, which models follow when sampling an element) | keep the order of `materials[]` and `components[]`; write numbers as `%.17g` |
| Placement positions | **yes** (one ulp changes step lengths) | in C++, keep the operation order of the old `Detector.cc` (`stack = Σ repeat × Σt`, `world = world_scale × stack` or `world.size_mm`, `x = −stack/2`, `center = x + t/2`, `x += t`); write as `%.17g`; the new `Detector.cc` computes the centre as `at + t/2` |
| `shift_mm ≠ 0` | **yes** | `(x + t/2) + shift` and `(x + shift) + t/2` need not be bit-identical; guaranteed only for `shift = 0` (J14 and the mirrors), otherwise a statistical comparison |
| Gun position | **yes** | `gun_world_fraction × world length`, computed in the same order and written out |
| Physics list composition | **yes** | `G4StepLimiterPhysics` only when `step_limit_mm > 0` or `min_ekin_MeV > 0` (task B adds: when a field is present) |
| Daughter placement order | low | keep the order |
| Material and region creation order | low (couple numbering only) | keep the order |
| Volume names, copy numbers | no (output column names only) | unchanged |
| Overlap check | no (uses its own `G4QuickRand`) | — |
| Output column set and order | affects the comparison | a spec converted from spec/1 enables the old scorer set, in `CsvColumns` order |

**Acceptance:** on the same host and Geant4 build, the layered_sim from before phase 2 and the new one give bit-identical CSVs (same seeds, serial) for TestEm3, the TestEm5 mirror and the J14 specs, and identical hex-float dumps of every placement (name, copy number, translation, mother). Across hosts only a statistical comparison; the committed J14 CSVs are not a bit-level reference.

### A2.7 Column map

- File `column_map.json`, schema `layered_sim.output/2`, kept in the adapter next to `output.schema.json`.
- layered_sim writes it for every run; its hash goes into the run record.
- Each column has a semantic name, the actual column name, a unit and an operational definition; `column_map_version`.
- It describes both the CSV columns and the columns of every ntuple in the ROOT file (each column states `file: csv | root` and its `ntuple`).
- A user's own application can write a map of the same format by hand; only declarative operations (rename, unit, sum, filter) are allowed. A conversion that computes something must be a separate recorded step.

### A2.8 `simcore` (C++ compute core)

| Item | Rule |
|---|---|
| Location | `adapters/geant4/assets/simcore/` (a CMake project; owner hep-detector) |
| Dependencies | the C++17 standard library and the existing `MiniJson.hh`; no Geant4, no third-party libraries |
| Executables | `simspec`, `simstat` (task B adds `simreco`) |
| Interface | input: spec, CSV, column map, parameter JSON (no ROOT files; `simroot dump` converts them to CSV when needed). Output: one JSON object (stdout or `--out`) with `status`, `program` (name, version, compiler) and the results |
| Exit codes | 0, 1, 2, 3 (section 2, rule 6) |
| Numerics | double; order-independent sums (sorted first or compensated), so results do not depend on threads or chunk order; random numbers only from a counter hash (SplitMix64), never `<random>` distributions (their output differs between implementations) |
| Output precision | floating point as `%.17g` |

`simstat` subcommands (replacing computations that are in Python today):

| Subcommand | Content | Replaces |
|---|---|---|
| `summarize` | per-run observables: mean deposit, tail fraction, leakage fractions, MPV (fixed bin width), E_in − E_exit of transmitted primaries; columns read through the column map | the computation in `check_geant4_study.py summarize`; the Geant4-side statistics in `geant4_benchmarks.py` |
| `subrun` | MPV of each chunk CSV, their mean and sd/√K | the estimator of A1.6 |
| `bootstrap` | SE under Poisson(1) counter-hash weights (means, quantiles, fractions); all observables of an event share its weight | `bootstrap()` |
| `diff` | the difference of observables between two scan points and the SE of the difference | the numerical part of `convergence()`; the decision stays in Python |
| `balance` | per-event energy-balance residuals | the numerical part of `geant4_verify.py balance` |

- **Migration and equivalence:** phase 1's Python estimators move to `tests/` as oracles only. The equivalence test compares `simstat` with the oracle on J14's recorded CSVs: identical counts, the MPV in the same bin, other floating-point values within a relative difference of 1e-12 (different summation order).
- **Why no Python bindings:** separate executables keep the Python side standard-library only and free of compilation; outputs are hashed files that go straight into provenance; the G5 approval wording needs no change.
- **Trace:** `simcore` runs in another process and never appears in `code_paths`. The Python interface that calls it writes the sha256 of the executable and its sources, the version and the subcommand into the record, and tags the call with `trace.tag()` (for example `geant4-simstat`).

### A2.9 Per-event ROOT files

Detailed per-event simulation information is written to ROOT files (user decision, 2026-10-22). The per-event CSV stays as the summary table: its existing columns, the bit-identical comparison of A2.3 and the input of `simstat` are unchanged.

| Item | Rule |
|---|---|
| Writing | `layered_sim` writes through `G4AnalysisManager` (ROOT output type), built on the g4tools code shipped with Geant4; no ROOT installation, no new build dependency |
| Settings | `output.event_file` in spec/2: `level` is `none` (default; J14 unchanged), `summary` or `hits` (task B adds `crossings`); `compression` (default 1); `max_events_hits` (default 100) |
| Files | one file per run (per chunk); under MT, `SetNtupleMerging(true)` makes the master merge into one file (in 11.4.3 only the ROOT output supports ntuple merging); the path goes into the run record through `tilde()` |
| Layout | flat ntuples with scalar columns only (I, D, S); every row carries a key (`event_id` plus the ntuple's own secondary key); no vector columns, so ROOT and uproot read them directly as tables |
| Row order | after MT merging the row order depends on thread scheduling and must not be relied on; readers always sort by key first |
| When written | rows filled in `EndOfEventAction`; the file is written and closed at the end of the run. An interrupted run leaves an incomplete file; the run is incomplete (exit 3) and nothing goes into `output_hashes` |
| Version | the layout is `layered_sim.events/1`, and the file carries `event_file_version`; the column map allows more ntuples (task B adds `crossings` and increments the version) |

Ntuples (units and operational definitions in the column map):

| Ntuple | Level | One row per | Columns |
|---|---|---|---|
| `run` | from `summary` | file | sha256 of spec and column map, layered_sim version and source hash, Geant4 version, seeds, chunk index, event count, `event_file_version`, process-number table |
| `events` | from `summary` | event | `event_id`, primary PDG code, kinetic energy, origin, direction; total deposit per subsystem; energy leaving the world volume; flags |
| `deposits` | from `summary` | event × volume with a deposit | `event_id`, `volume_id`, `copy`, total deposit, deposit by charged particles; volumes without a deposit are not written |
| `hits` | `hits` only | step with a deposit | `event_id`, `track_id`, `parent_id`, PDG code, `volume_id`, `copy`, pre- and post-step positions, time, deposit, step length, process number |

- `hits` is large (a GeV shower in a calorimeter has tens of thousands of steps) and is for small samples only: spec validation rejects (`rejected`, exit 2) an event count above `max_events_hits`.
- **Content hash:** a ROOT file's bytes include the write time and similar information, so two identical runs never give bit-identical files. The run record keeps both the file sha256 (integrity only) and the `content_sha256` from `simroot hash` (comparison and provenance); bit identity is required only of the CSV and of `content_sha256`. Under MT the master draws every event's seeds in advance, so an event's content does not depend on the thread, and two runs with different thread counts should give the same `content_sha256`.
- **Consistency:** each quantity is computed once, by one scorer, and written to both the CSV and the ROOT file.
- **Size:** ROOT files are not committed; the run record keeps the path, file sha256, `content_sha256`, row count per ntuple and file size; ROOT files needed by tests are produced in live tests. At the `summary` level an event takes about 120 B before compression (`events`) plus 28 B per volume with a deposit (`deposits`).
- **G5:** Python still exchanges only JSON and CSV with separate executables, so the boundary wording is unchanged; ROOT files are written and read only by `layered_sim` and `simroot`, which link Geant4, through Geant4's own analysis module. The VALIDATION entry names the new file type and `simroot` for the reviewer to confirm.

### A2.10 `simroot` (reading ROOT files)

Python never parses ROOT, and `simcore` does not link Geant4. Reading is done by `simroot`, in the same CMake project as `layered_sim`, linking only Geant4's analysis library (`G4RootAnalysisReader`, also built on g4tools) and creating no run manager. Exit codes per section 2, rule 6.

| Subcommand | Content |
|---|---|
| `info` | row count and columns of each ntuple and the contents of the `run` row; JSON output |
| `dump` | writes the chosen ntuples and columns as CSV (stdout or `--out`) after sorting by key, floating point as `%.17g`; reads several chunk files at once; `--events` selects a subset |
| `hash` | content hash: each ntuple sorted by key, values normalized as hex floats, then sha256; outputs `content_sha256` |

- Downstream: `simstat` reads only CSV; task B's `simreco` reads the output of `simroot dump` (through a pipe, not stored). Researchers may analyze ROOT files directly with ROOT or uproot (hep-computing's root-uproot adapter), but neither is a dependency of the pipeline or the required tests.
- How `G4RootAnalysisReader` handles string columns, several files and large files has not been checked with real files yet (§12, risk 9); if the round-trip test shows a gap, `simroot` reads only flat scalar columns and the strings of `run` move to a JSON side file.

## 12. Decisions for the maintainer and residual risks

**To decide:**
1. The version class of phase 1: following the convention of gates at x.y.0, this document makes it C1 (minor) plus a sci-fix.
2. Whether a statistical comparison is acceptable if bit-identical output cannot be reached even on the same host (with the reason recorded in VALIDATION).
3. How to confirm the G5 statement that no example code was copied.
4. The optional `simulation` property in `ext_computational_run.json`: hep-computing must agree.
5. A new required CI job that builds `simcore` (needs a C++17 compiler); the adapter has no required CI job today.
6. Where ROOT files are stored and for how long (not in the repository; proposed: hep-computing's run directory, matched to the run record by hash).

**Residual risks:**
1. J14's detection limits may change with the sub-run estimator, t quantiles and controls in observable units; the controls may need to be redesigned.
2. The mean of sub-run MPVs and the full-sample MPV differ slightly (about 0.25 % in a reviewer's toy); the sci-fix record explains this.
3. Only 931 bytes of quick-load budget remain.
4. The probe assumes that workers have the master's settings; if a thread-local difference appears, dump per thread.
5. For `longitudinal-profile`, `target_slabs` is declared by a person; the contract can only compare the declared and benchmark `target_geometry_sha256`, not decide that the target stack is the one in the paper, which a reviewer still checks.
6. Effort: the prototype estimates phase 1 at about 8–12 engineer-days plus Geant4 time (A1.1, A1.2 and A1.10 about 1 day; A1.3 1–2 days; A1.4 1–2 days; A1.5–A1.9 3–5 days; the sci-fix process about 1 day). Phase 2 is not estimated.
7. Two languages to maintain: principle 11 and the equivalence tests keep one production implementation per quantity.
8. Floating-point equivalence: compilers and optimizations (FMA, say) can make `simstat` and the oracle differ in the last digits; the equivalence test uses a relative difference of 1e-12, and bit identity is required only of the simulation output and `simspec`'s placement values (same build).
9. How `G4RootAnalysisReader` reads string columns, several files and large files has not been checked with real files; the round-trip test of A2.12 settles it (fallback in A2.10).
10. Disk and memory: ROOT files of large samples can reach hundreds of MB; with MT merging, worker baskets stay in memory until the end of the run. `hits` has an event-count limit; size and memory are checked in a trial run and recorded.

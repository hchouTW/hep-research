## 0. Summary

Task A has two phases: it fixes correctness defects in the Geant4 part of hep-research (from 0.20.0 to the current main) and moves the compute core to C++, removing the coupling of the study workflow to a single simulation backend. The J15 minimal spectrometer is a separate, independent task (task B), done after task A (section 6).

| Phase | Content | Version | J14 |
|---|---|---|---|
| 1 | Fix label and statistics defects (sci-fix): scope compares the observable kind; benchmark grades come from a contracts table; configuration derived from the geometry, with the isolation rule enforced; negative controls judged by the shift in the observable; convergence gate as an intersection-union test; MPV SE from a partition into sub-runs | **contracts C1** (minor) | 4.1–4.3 regenerated by offline replay; one live re-record for 4.4 and 4.5 |
| 2 | C++ compute core: layered_sim refactor (spec/2, scorer components, probe, column map, per-event ROOT files) and the new `simcore` (spec conversion, observables and statistics) and `simroot`; Python becomes the interface; hep-detector reads both formats | **adapter 0.2.0**; no contracts version change | re-recorded once, after bit-identical output on the same host |

**The eight most important decisions:**

1. **The current `validated-in-scope` has holes and must be fixed first.** The scope check skips the observable, and
   the grade of a benchmark is declared by the record itself.
2. **The contract enforces upgrade eligibility.** The contracts carry their own table of benchmark → grade and kinds;
   `configuration` is derived by the tool from the geometry, re-derived by `dependencies.py`, and never taken from user input.
3. **One geometry path in C++.** spec/1 is converted to spec/2 by the C++ `simspec` (keeping the old geometry's floating-point operations); bit-identical output on the same host proves the conversion.
4. **Reuse existing tools.** `contracts/schema.py`, `tracker_resolution.py` and `multiple_scattering.py`; no second
   implementation.
5. **The statistical rules must be executable.** The convergence gate is an intersection-union test; t quantiles
   whenever the SE is estimated; the two-stage event-count factor is F₀.₉₀(15,15) ≈ 1.97; unresolved gates and missed targets are reported as `incomplete` (exit 3), not `failed`.
6. **Drop or defer what is not needed.** `uses-validated-physics`, `physics_config_comparison`, a content-addressed cache, contracts 4.0 and more (section 7).
7. **The compute core is C++; Python is the interface and judgement layer.** Simulation, scorers, spec conversion, observables and statistics are in C++ (`layered_sim` and the Geant4-free `simcore`; task B adds digitization and reconstruction), exchanging JSON/CSV through separate executables. Python handles only the command line and workflow, the independent reference formulas, rule and gate decisions, labels, record writing and the contracts; C++ and Python are therefore independent implementations of each other (section 3).
8. **Detailed per-event information is stored in ROOT files.** They are written by the g4tools code shipped with Geant4, with no ROOT installation; flat ntuples keyed by `event_id`. Python and `simcore` never read ROOT directly: the new `simroot` converts to CSV or gives a content hash; the per-event CSV stays as the summary table (5.9).

## 2. Design principles

1. **Correctness before extension.** No new feature is merged before phase 1 is complete.
2. **The study core reads only data.** Rules, gates and benchmarks read through the column map and the probe output,
   never backend-specific column names or UI command strings.
3. **Trust the effective state; declarations are only a fallback.**
4. **Stopping rules and grids for evidence are declared in advance.** Extra runs, refinements and repeated controls
   are never decided by gate or benchmark outcomes.
5. **Look for an existing implementation first.** Methods the plugin already has are reused; an oracle never imports
   the module under test.
6. **Minimal change.**
7. **Follow the existing rules.** Layering (skill scripts and adapters import only `core` and `contracts`), the
   quick-load limit (hep-detector is at 24,669 / 25,600 bytes), the G5 licence boundary, the adapter-change process, the sci-fix process, run statuses and exit codes (`core/status.py`) and the execution trace (`trace.provenance()`). A new shared module in `core/` needs a steward in `core/OWNERS.json`; experiment names must not appear in `skills/` and `contracts/` (`check_layering.py`). The Geant4 scripts use only the Python standard library; this is a design choice, not a plugin-wide rule. The C++ side uses only the C++17 standard library and the existing `MiniJson.hh`; `simcore` does not link Geant4; `layered_sim` and `simroot` also link Geant4 (ROOT files are written and read by the g4tools code shipped with Geant4, with no ROOT installation).
8. **Backends describe themselves.** layered_sim writes its own column map and its effective settings at run time.
9. **The validation grade follows the nature of the reference.** If the reference is an **exact consequence** of the
   inputs (analytic helix, kinematics, least-squares algebra), the check is verification and cannot upgrade; only if the reference is a **physics model that Geant4 approximates** (Bethe, Landau–Vavilov, Highland, shower profile) or a **published measurement** can it be reference or sanity.
10. **The contract decides what can upgrade.** Grade, kind and configuration are never self-declared by a record.
11. **Language split.** Every computation that turns simulation output into numbers (per-event and per-run reductions, estimators and their SE, fits) is in C++; formulas that compute reference values from physics inputs, threshold comparisons and decisions, records and provenance, and the contracts are in Python. No quantity has a production implementation in both languages; an implementation in the other language may exist only in tests, as an oracle.

## 3. Architecture overview

**Language split** (user decision, 2026-10-22):

| Layer | Language | Content |
|---|---|---|
| Compute core | C++ | `layered_sim` (links Geant4): simulation, scorers, probe, column map, per-event ROOT files. `simroot` (links only Geant4's analysis library): reads ROOT files, converts to CSV, content hash. `simcore` (C++17 standard library, no Geant4): `simspec` (spec/1 → spec/2 conversion), `simstat` (observables, MPV and sub-runs, bootstrap, convergence differences and their SE, energy-balance residuals), `simreco` (task B: digitization, fits, β, calorimeter) |
| Interface | Python | `adapters/geant4/assets/*.py`: command line, builds, running the C++ executables, schema and cross-field validation of specs, writing records (with `trace.provenance()`), simulated tables |
| Judgement and references | Python | hep-detector: rules, independent reference formulas (Bethe, Δp, Highland, gamma profile, PSTAR), gate and benchmark decisions, labels; an independent implementation relative to the C++ computation |
| Contracts | Python | `contracts/` (shared by the whole plugin; unchanged) |

C++ and Python exchange only JSON/CSV through separate executables, as `layered_sim` does today; there are no Python bindings. The Python side therefore stays standard-library only and needs no compilation, and the G5-approved boundary ("a separate executable exchanging JSON and CSV") is unchanged. `simcore` does not link Geant4, is outside the Geant4 licence, and can be built and tested in CI without Geant4.

Detailed per-event information is written to ROOT files (5.9), written and read by the g4tools code shipped with Geant4, with no ROOT installation. Neither Python nor `simcore` reads ROOT directly; they go through `simroot`, which converts to CSV or gives a content hash, so the boundary above still holds.

## 4. Phase 1: fix the current defects (contracts C1, sci-fix)

Phase 1 is a sci-fix: the defects are fixed with minimal change in the existing Python. The estimators of 4.5 (sub-run MPV, bootstrap, convergence differences) move to the C++ `simstat` in phase 2; phase 1's Python implementations then stay only in tests, as oracles (5.8).

### 4.1 A benchmark table in the contracts (D2)

Add a constant table to `contracts/validate.py`. `_study_upgrade` takes grades and kinds from this table, not from the
record:

| Benchmark | Grade | Supported observable kinds |
|---|---|---|
| `stopping-power` | reference | `stopping-power` |
| `range` | reference | `range` |
| `thin-layer-mpv` | reference | `most-probable-value` |
| `thin-layer-width` | sanity | `thin-layer-width` |
| `multiple-scattering` | sanity | — |
| `em-shower-shape` | sanity | — |
| `shower-containment` | sanity | — |
| `longitudinal-profile` | reference | `shower-maximum` (a new kind; it measures t_max only) |
| `published-data` | interface | — |

- The grades equal the current `GRADES` (9 names; the prototype added a test for it). J14's verdicts do not change, but every study and benchmark file does (new fields; `code_paths` gains `contracts/validate.py` and others).
- A record whose `grade` disagrees with the table, or whose benchmark name is not in it, is an error; this applies to every record with a Geant4 study block, not only upgraded ones.
- `GRADES` in `geant4_benchmarks.py` stays for the tool; a test keeps it equal to the contracts table. The kinds a benchmark supports come only from the contracts table; kinds the tool prints are informational.

### 4.2 Scope check (D1)

- Compare the controlled `observable.kind` (the study spec's existing enum), not free text; the free text stays for
  human readers.
- `label` copies the declared kind from the study spec's `observable.kind` into `declared_scope.observable_kind` (the study spec's `validation_plan.scope` has `additionalProperties: false`, so the schema gains this field too); it must be among the kinds supported by the counted benchmark.
- Every dimension in the benchmark's scope must be in the declared scope; a missing dimension counts as outside (today a missing dimension is unconstrained).
- Dimensions compared: observable kind, particle, material, energy, thickness; a scalar is treated as `[v, v]`.
- One implementation in `validate.py`, exported; `check_geant4_study.py` imports it and `scope_within()` is removed.
- Gated like every other rule family: `strict or _at_least(contract_version, C1)`, with no warning branch. Records at contract 3.5.0 or below meet the new rules only under `--strict`, and only those carrying `validated-in-scope` fail (`_study_upgrade` returns early for the others).
- The scope of `longitudinal-profile` holds only particle and energy (the tool emits null material and thickness for it); the comparison uses these two dimensions, the kind and the **target-geometry hash**: the declared scope must carry the same `target_geometry_sha256` as the benchmark (4.3). Comparing only particle and energy would let any material stack upgrade on the published stack's result (the prototype showed this loosening). The energy is a scalar, so the declared energy range must equal it.

### 4.3 configuration and the isolation rule (phase 1)

- `geant4_benchmarks.py` emits `configuration`, `target_geometry_sha256` and `configuration_basis` for each benchmark result, derived from the geometry of the run record named by the benchmark's `run_record`, never from user input. A benchmark counted for an upgrade must have `run_record` (optional today).
- **Target:** the benchmark configuration declares `target_slabs` (the slab names in the target, absorbers included). For single-slab benchmarks the default is the measured slab; `longitudinal-profile` must list the whole sampling stack. Its `layers` list only readout columns, not absorbers, so the stack cannot be derived; the prototype showed that a literal derivation makes every real sampling stack `embedded`.
- `isolated` requires: no field, a vacuum world (`G4_Galactic`; J14 qualifies), and every placement other than the world in `target_slabs`; otherwise `embedded`. spec/1 has no field key and counts as field-free; spec/2 is judged by its explicit `field` block, checked against the probe's recorded field from phase 2.
- `target_geometry_sha256`: the hash of a canonical list of the target (ordered slabs, thickness, transverse size, material composition and density; numbers as `repr`; repeated placements listed one by one), the same for spec/1 and spec/2.
- **Contract rule (C1, gated as in 4.2):** every counted benchmark must have `configuration == "isolated"`; missing or `embedded` is an error. `dependencies.py` **must** re-derive configuration and the hash from the run records in `evidence_records` and compare them with the record; otherwise configuration would be self-declared like the grade.
- Confirmed by the prototype: configuration can be derived from the existing recorded run records, so J14 gains `configuration: isolated` by offline replay, without a live re-record.
- Residual limit: J14's recorded CSVs are reduced, so their hashes cannot match the run records' `output_hashes`. configuration describes the run record the configuration **names**, not one proven to have produced the CSV; the protocol says so. The geometry of negative-control runs is not checked separately.

### 4.4 Negative controls (D3)

- The decision quantity is the realized shift in the observable: `shift = (control − nominal) / reference`, with the
  SE combined from both runs.
- At the detection limit: `caught` and `|shift| ≤ 1.1 × DL`.
- Inject both signs; otherwise restrict the claim to one sign and record it in `scope.detection_limit_sign`.
- J14's existing controls inject +density only. Phase 1 first restricts both J14 claims to one sign (`detection_limit_sign: "+"`); per the prototype both already meet `|shift| ≤ 1.1 × DL` (MPV 0.0856 against DL 0.0827; stopping power 0.0381 against 0.0378). The live re-record adds the negative controls.

### 4.5 Statistical rules

**Convergence gate (D4).** "Pass only if every observable is equivalent" is an intersection-union test:

```
pass:        |diff| + q_pass · se ≤ tol
fail:        |diff| − q_fail · se > tol
otherwise:   unresolved
```

| Item | Rule |
|---|---|
| se | the SE of the **difference** |
| q_pass | se from sub-runs: t₀.₉₅(ν); se from a large-sample bootstrap: z₀.₉₅ = 1.645 |
| q_fail | the same, at quantile 1 − α/m, with m the number of (parameter × observable) pairs |
| ν | difference of two estimates, each from K = 16 sub-runs: about 30 by Welch (t₀.₉₅(30) = 1.697); a single estimate: 15 |
| Event count | set in advance so that the se of the difference ≤ tol/4 |

Operating characteristics (se = tol/4 taken as known, α = 0.05):

| True difference | Pass | Fail (m = 1) | Fail (m = 6) | Fail (m = 30) |
|---|---|---|---|---|
| 0 | 0.981 | 0.000 | 0.000 | 0.000 |
| tol/2 | 0.639 | 0.000 | 0.000 | 0.000 |
| tol | 0.050 | 0.050 | 0.008 | 0.002 |
| 2 tol | 0.000 | 0.991 | 0.946 | 0.857 |

At a true difference of tol/2 the gate passes only about 64 % of the time; this is the price of se ≤ tol/4 and is stated in the documentation.

**Reporting.** An unresolved gate is reported with run status `incomplete` (exit 3) and the artifact label stays `unvalidated`; only a fail is `failed` (exit 1). Today `convergence()` and `cmd_run` turn anything but pass into `failed`, which must change.

**MPV estimator and its SE (D5).**
- The nominal sample is produced as K = 16 chunks (`geant4_run.py chunk` with a hand-built partition manifest), N events in total. This is **not** a split of the existing single nominal run: every chunk holds new events, so J14's nominal needs a live re-record. The full sample is the concatenation (`concat`) of the chunk CSVs.
- The reported value becomes **the mean of the 16 sub-run MPVs**, with a fixed bin width written in the spec;
  SE = sd(sub-run MPVs) / √16; quantiles from t₁₅.
- The full-sample MPV is a diagnostic only; its difference from the mean is recorded. The histogram-mode estimator does
  not scale as 1/√N, and sd/√K is valid only for the mean of the sub-run MPVs. A reviewer's toy showed that applying
  it to the full-sample MPV underestimates the SE by a factor of 1.1 to 2.3, depending on the bin width.
- The bootstrap is no longer used for the MPV.
- Sub-run MPVs are computed from each chunk's CSV, never through the partition merge rules (`mpv` is not in `NON_ADDITIVE_TOKENS`, so as a chunk value key it would be summed silently).

**Two-stage event count.**
- `N = ceil(N_trial · (SE_trial / target)² · f)`.
- "Target missed" is judged on the **estimated** SE of the evidence run. When both the trial and the evidence SE come
  from K = 16 sub-runs, the probability of meeting the target is P(F₁₅,₁₅ ≤ f): only 0.636 at f = 1.2, so
  **f = F₀.₉₀(15,15) ≈ 1.97**, which gives 90 %.
- When the SE comes from a large-sample bootstrap, f = 1.2.
- An evidence run that misses the target is unresolved (`incomplete`, exit 3) and **must not be topped up**.

**Seeds.** `H(study_id, role, point_id, k)` maps to **one** integer in [1, 2³¹) (the C++ reads seeds as doubles and loses precision above 2⁵³). Roles: trial, nominal, scan, control, variation, calibration; k is the chunk index; the two signs of a control use different point_ids.
- chunks: the study builds the manifest by hand, with chunk seed H; layered_sim's second seed stays `cmd_chunk`'s `start + 1`. `make_manifest`'s `seed × 100003 + k` is not used.
- scans: each point's seed is H, not `cmd_scan`'s `[s0, s1 + k]`.
- check: `validate_manifest` refuses duplicate seeds only within one manifest; `check_geant4_study.py` also checks that no seed pair repeats across all run records of a study.

**Bootstrap** (for means, quantiles and fractions).
- Poisson(1) weights from a 64-bit counter hash of (study_seed, run_id, chunk_id, event_id, replica_id), mapped by the
  inverse CDF.
- R ≥ 400.
- `summarize` checks the event keys for duplicates.

**Correlated evidence (D7).** `extension.study.evidence_overlap` lists runs shared by several decisions, with `evidence_overlap_version`.

**Execution trace.** New shared functions call `trace.tag()` (lower-case words joined by hyphens): the scope comparison `geant4-scope-kind`, configuration derivation `geant4-configuration`, the IUT gate `geant4-convergence-iut`, the sub-run MPV `geant4-mpv-subrun`, the seed hash `geant4-seed-hash`. The advisory scan does not read tags yet, but a later advisory can use them to tell whether the affected code ran. Once `check_geant4_study.py` imports `contracts.validate`, study records' `code_paths` gain `contracts/validate.py` and others, as expected. From phase 2, the sub-run MPV and the bootstrap run in `simstat` (another process), and their tags are recorded by the Python interface that calls it (5.8).

- [ ] Negative controls are judged by the shift in the observable, with tests for both signs.
- [ ] Gate toy test (10⁴ toys per cell): pass rate ≤ 0.05 + 3σ_MC at a true difference of tol; ≥ 0.97 at 0; the fail rates (m = 1, 6, 30) match the table in 4.5 within 3σ_MC; unresolved is reported with exit 3.

## 5. Phase 2: C++ compute core (adapter 0.2.0)

### 5.1 Scope

All C++ work that affects J14 happens in this phase: reading spec/2, scorer components, the probe, the column map, and moving the computation of observables and statistics from Python to the new `simcore` (5.8). The
field region and plane crossings arrive in task B (mixtures already exist in 0.21.0); they change the
`sources_sha256` of later live J14 reruns, which is expected, and the committed J14 records are not re-recorded.

### 5.2 spec/2 coordinates and format

- Coordinates are centred on the world; the stack axis is x.
- `at_mm` is the x coordinate of an element's **front face** in world coordinates. A daughter's `at_mm` is also in
  world coordinates and must lie inside its mother.
- One level of nesting only.
- The schema uses only keywords supported by `contracts/schema.py` (including the three added in this phase).
- The schema reserves an optional `field` block (implemented in task B); in this phase `layered_sim` rejects a non-empty `field` (`rejected`, exit 2).

### 5.3 spec/1 → spec/2 conversion and bit-identical output

| Factor | Effect | Conversion rule |
|---|---|---|
| Material creation | **yes** (mixtures add components in order with `G4Material::AddMaterial`; the order sets the order of the material's element vector, which models follow when they sample an element from a random number, so events change, not only the floating-point sum of mass fractions) | keep the order of `materials[]` and `components[]`; write numbers with `%.17g` |
| Placement positions | **yes**: one ulp changes the step lengths | the conversion runs in the C++ `simspec convert`, keeping the operation order of the old `Detector.cc` (`stack = Σ repeat × Σt`, `world = world_scale × stack` or `world.size_mm`, `x = −stack/2`, `center = x + t/2`, `x += t`), with output as `%.17g`; the new `Detector.cc` computes the centre as `at + t/2`. The same language and the same double arithmetic are more reliable than reproducing the floating-point order in Python |
| `shift_mm ≠ 0` | **yes** | `(x + t/2) + shift` and `(x + shift) + t/2` are not guaranteed bit-identical; guaranteed only for `shift = 0` (J14 and the mirrors), statistical comparison otherwise |
| Gun position | **yes** | `gun_world_fraction × world length`, computed in the same order and written out |
| Physics list composition | **yes** | `G4StepLimiterPhysics` only when `step_limit_mm > 0`, `min_ekin_MeV > 0` or (task B) a field is present |
| Daughter placement order | low | keep the order |
| Material and region creation order | low (only couple indices) | keep the order |
| Volume names, copy numbers | **none** (only output column names) | keep unchanged |
| Overlap checks | **none** (they use the separate `G4QuickRand`) | — |
| Output column set and order | affects comparison | specs converted from spec/1 enable the legacy scorer set, in `CsvColumns` order |

**Acceptance:** on the same host and Geant4 build, the layered_sim from before phase 2 and the new one produce bit-identical CSVs
for the TestEm3 and TestEm5 mirrors and the J14 specs (same seeds, serial), and identical hex-float dumps of every
placement (name, copy number, translation, mother). Across hosts, only statistical comparison; the committed J14 CSVs
are not a bit-identical reference.

### 5.6 Probe and column map

**Probe (`Probe.hh`):**

| Item | Rule |
|---|---|
| Timing | the master's `BeginOfRunAction`; state `G4State_GeomClosed` and more than zero couples; otherwise it writes `effective_config: {"recorded": false, "reason": ...}` and layered_sim still exits 0 (not "refused": in `core/status.py` that means a negative verdict). Per the 11.4.3 source, the physics tables exist at this point; a fake run (`/run/beamOn 0`) returns before `BeginOfRunAction`, so the probe does not run |
| Frequency | once per run |
| Threads | master only; the output says "workers assumed identical" |
| EM parameters | full text of `G4EmParameters::StreamInfo(os)` plus parsed fields; not `Dump()` (in 11.4.3 it prints only once per process) |
| Cuts | per material-cuts couple: material, region, range cut, energy threshold per particle |
| Hadronic models | per process and model, energy ranges queried per material and element; overlap regions marked as random choice |
| Run manager | type, `seedOncePerCommunication`, `G4RUN_MANAGER_TYPE`; SubEvt or a non-zero seeding mode is reported as a gap |
| Other | `G4UserLimits`, biasing, dataset paths and content hashes |
| Paths | written through `tilde()` (`check_packaging.py` scans every text file) |
| Version | 11.4.x; `probe_version` |
| Output | `extension.simulation.effective_config` |

Rules and the model assignment of variations read the probe first and fall back to declarations, writing
`source: probe | declared`; when both exist and disagree, it is an error.

**Test trigger:** a UI command present only in test builds calls the probe after `/run/initialize` and before the first `BeamOn`; the probe must write `recorded: false`.

**Column map:**
- File `column_map.json`, schema `layered_sim.output/2`, kept in the adapter next to `output.schema.json`.
- layered_sim writes it for every run; its hash goes into the run record.
- Each column has a semantic name, the actual column name, a unit and an operational definition; `column_map_version`.
- It describes both the CSV columns and the columns of every ntuple in the ROOT file (each column states `file: csv | root` and its `ntuple`).
- A user's own application can write a map of the same format by hand; only declarative operations (rename, unit,
  sum, filter) are allowed. A conversion that computes something must be a separate recorded step.

### 5.8 C++ compute core `simcore`

| Item | Rule |
|---|---|
| Location | `adapters/geant4/assets/simcore/` (a CMake project; the adapter's owner is hep-detector) |
| Dependencies | the C++17 standard library and the existing `MiniJson.hh`; no Geant4, no third-party libraries |
| Executables | `simspec`, `simstat` (this phase); `simreco` (task B) |
| Interface | input: spec, CSV, column map, parameter JSON (no ROOT files; when needed, `simroot dump` converts them to CSV); output: one JSON object (stdout or `--out`) with `status`, `program` (name, version, compiler) and the results |
| Exit codes | per `core/status.py`: 0 ok, 1 a negative verdict, 2 unusable input (`rejected`), 3 incomplete; no other exit code |
| Numerics | double; sums are order-independent (sorted first or compensated), so results do not depend on threads or chunk order; random numbers only from a counter hash (SplitMix64), never from the standard library's `<random>` distributions (their output differs between implementations) |
| Output precision | floating point written as `%.17g`, so it round-trips exactly |

`simstat` subcommands (replacing computations that are in Python today):

| Subcommand | Content | Replaces |
|---|---|---|
| `summarize` | per-run observables: mean deposit, tail fraction, leakage fractions, MPV (fixed bin width), E_in − E_exit of transmitted primaries; columns read through the column map | the computation in `check_geant4_study.py summarize`; the Geant4-side statistics in `geant4_benchmarks.py` |
| `subrun` | MPV of each chunk CSV, their mean and sd/√K | the sub-run estimator of 4.5 |
| `bootstrap` | SE under Poisson(1) counter-hash weights (means, quantiles, fractions); all observables of an event share its weight | `bootstrap()` |
| `diff` | the difference of observables between two scan points and the SE of the difference | the numerical part of `convergence()`; the decision stays in Python |
| `balance` | per-event energy-balance residuals | the numerical part of `geant4_verify.py balance` |

**Migration and equivalence.** Phase 1's Python estimators move to `tests/` as oracles only and leave the production code. The equivalence test compares `simstat` with the Python oracle on J14's recorded CSVs: counts identical, the MPV in the same bin, other floating-point values within a relative difference of 1e-12 (from different summation order). If either side later changes its algorithm, the other remains an independent implementation.

**Why no Python bindings.** Separate executables keep the Python side standard-library only and free of compilation; the outputs are hashed files that go straight into provenance; the G5 approval wording needs no change.

**Trace.** `simcore` runs in another process and never appears in `code_paths`. The Python interface that calls it writes the sha256 of the executable and its sources, the version and the subcommand into the record, and tags the call with `trace.tag()` (for example `geant4-simstat`).

### 5.9 Per-event ROOT files

Detailed per-event simulation information (event truth, per-volume deposits and, when needed, per-step hits; task B adds plane crossings) is written to ROOT files (user decision, 2026-10-22). The per-event CSV stays as the summary table: its existing columns, the bit-identical comparison of 5.3 and the input of `simstat` are unchanged.

| Item | Rule |
|---|---|
| Writing | `layered_sim` writes through Geant4's `G4AnalysisManager` (ROOT output type), built on the g4tools code shipped with Geant4; no ROOT installation and no new build dependency |
| Settings | `output.event_file` in spec/2: `level` is `none` (default; J14 unchanged), `summary` or `hits` (task B adds `crossings`); `compression` (default 1); `max_events_hits` (default 100) |
| Files | one file per run (per chunk); under MT, `SetNtupleMerging(true)` makes the master merge into a single file (in 11.4.3 only the ROOT output supports ntuple merging); the path goes into the run record through `tilde()` |
| Layout | flat ntuples with scalar columns only (I, D, S); every row carries a key (`event_id` plus the ntuple's own secondary key); no vector columns, so readers do not depend on vector-column support, and ROOT and uproot read them directly as tables |
| Row order | after MT merging the row order depends on thread scheduling and must not be relied on; readers always sort by key first |
| When written | rows are filled in `EndOfEventAction`; the file is written and closed at the end of the run. If the run is interrupted the file is incomplete, the run is incomplete (exit 3) and nothing goes into `output_hashes` |

Ntuple layout `layered_sim.events/1` (column units and operational definitions are in the column map):

| Ntuple | Level | One row per | Columns |
|---|---|---|---|
| `run` | from `summary` | file | sha256 of spec and column map, layered_sim version and source hash, Geant4 version, seeds, chunk index, event count, `event_file_version`, process-number table |
| `events` | from `summary` | event | `event_id`, primary PDG code, kinetic energy, origin, direction; total deposit per subsystem; energy leaving the world volume; flags |
| `deposits` | from `summary` | event × volume with a deposit | `event_id`, `volume_id`, `copy`, total deposit, deposit by charged particles; volumes without a deposit are not written |

| `hits` | `hits` only | step with a deposit | `event_id`, `track_id`, `parent_id`, PDG code, `volume_id`, `copy`, pre- and post-step positions, time, deposit, step length, process number |

Task B adds the `crossings` level and the ntuple of the same name (one row per event × crossed plane; B5) and increments `event_file_version`.

`hits` is large (a GeV shower in the calorimeter has tens of thousands of steps) and is for small samples only: spec validation rejects (`rejected`, exit 2) an event count above `max_events_hits`.

**Reading: `simroot`.** The Python side stays standard-library only and never parses ROOT; `simcore` still does not link Geant4 and uses no third-party library. Reading is done by a new small executable, `simroot`, in the same CMake project as `layered_sim`, linking only Geant4's analysis library (`G4RootAnalysisReader`, also built on g4tools) and creating no run manager. Exit codes follow `core/status.py`.

| Subcommand | Content |
|---|---|
| `info` | row count and columns of each ntuple, and the contents of the `run` row; JSON output |
| `dump` | writes the chosen ntuples and columns as CSV (stdout or `--out`) after sorting by key, floating point as `%.17g`; reads several chunk files at once; `--events` selects a subset |
| `hash` | content hash: each ntuple sorted by key, values normalized as hex floats, then sha256; outputs `content_sha256` |

The bytes of a ROOT file include the write time and similar information, so two identical runs never give bit-identical files. The run record therefore keeps both the file sha256 (for integrity only) and the `content_sha256` from `simroot hash` (for comparison and provenance); bit identity is required only of the CSV and of `content_sha256`. Under MT the master draws every event's seeds in advance, so an event's content does not depend on which thread processes it, and two runs with different thread counts should give the same `content_sha256` (5.10 acceptance).

**Downstream.** `simstat` reads only CSV. Task B's `simreco` reads the CSV from `simroot dump` (passed through a pipe, not stored; B6). Researchers can analyze the ROOT files directly with ROOT or uproot (hep-computing's root-uproot adapter), but neither is a dependency of the pipeline or of the required tests.

**Consistency.** Each quantity is computed once, by one scorer, and then written to both the CSV and the ROOT file. Tests check that the CSV's total deposit per subsystem equals the per-event sum of `deposits` (relative difference ≤ 1e-12) and that `events` has as many rows as the CSV.

**G5.** Python still exchanges only JSON and CSV with separate executables, so the G5-approved boundary wording is unchanged; ROOT files are written and read only by `layered_sim` and `simroot`, which link Geant4, through Geant4's own analysis module. The VALIDATION entry names the new file type and `simroot` for the reviewer to confirm.

**Size.** ROOT files are not committed to the repository; the run record keeps only their path, file sha256, `content_sha256`, the row count of each ntuple and the file size, and ROOT files needed by tests are produced in live tests. At the `summary` level an event takes about 120 B before compression (`events`) plus 28 B per volume with a deposit (`deposits`); the J15 estimate is in B11. The actual size and the row count of each ntuple go into the run record.

## 11. Decisions for the maintainer and residual risks

**To decide:**
1. The version class of phase 1. This proposal follows the convention of gates at x.y.0 and makes it C1 (minor) plus a sci-fix.
2. Whether a statistical comparison is acceptable if bit-identical output cannot be reached even on the same host
   (with the reason recorded in VALIDATION).
3. How to confirm the G5 statement that no example code was copied.
4. The optional `simulation` property in `ext_computational_run.json`: the schema owner hep-computing must agree (the C2 "derived simulation" marker belongs to task B).
5. A new required CI job that builds `simcore` (needs a C++17 compiler); the adapter has no required CI job today.
6. Where ROOT files are stored and for how long (not in the repository; proposed: hep-computing's run directory, matched to the run record by hash).

**Residual risks:**
1. J14's detection limits may change with the sub-run estimator, t quantiles and controls in observable units; the
   controls may need to be redesigned.
2. The mean of sub-run MPVs and the full-sample MPV differ slightly (about 0.25 % in a reviewer's toy); the sci-fix
   record explains this.
3. Only 931 bytes of quick-load budget remain.
4. The probe assumes that workers have the master's settings; if a thread-local difference appears, dump per thread.

5. For `longitudinal-profile`, `target_slabs` is declared by a person; the contract can only compare the declared and benchmark `target_geometry_sha256`, not decide that the target stack is the one in the paper, which a reviewer still checks.

6. Effort: the prototype estimates phase 1 at about 8–12 engineer-days plus Geant4 time (4.1, 4.2 and 4.6 about 1 day; 4.3 1–2 days; 4.4 1–2 days; 4.5 3–5 days; the sci-fix process about 1 day). Phase 2 also needs the port of the statistics to `simstat` and the CI job, not estimated by the prototype.

7. Two languages to maintain: the core logic is split between C++ and Python; principle 11's split and the equivalence tests keep one production implementation per quantity.

8. Floating-point equivalence: compilers and optimizations (FMA, say) can make `simstat` and the Python oracle differ in the last digits; the equivalence test uses a relative difference of 1e-12, and bit identity is required only for `simspec`'s placement values (same build).

9. This proposal has not yet checked with real files how `G4RootAnalysisReader` handles string columns, several files and large files; the round-trip test of 5.10 settles it. If it falls short, `simroot` reads only flat scalar columns and the strings of `run` move to a JSON side file.

10. Disk and memory: ROOT files of large samples can reach hundreds of MB; with MT merging, worker baskets stay in memory until the end of the run. `hits` has an event-count limit; size and memory are checked in a trial run and recorded.
